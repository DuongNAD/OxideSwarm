# R21: what Mesh-LLM already does (reading of 2026-11-19)

Spike R21 of [design 0064](../../docs/design/0064-research-of-2026-11-13-and-route.md) asks what
Mesh-LLM already does of the model items that designs 0038, 0056, 0061, 0062 and 0067 plan.
Design 0064 places the records of R21 under `benchmarks/` (its Test plan). This file is part 1
of the spike: a reading of the project's documents, code, releases and pull requests. Part 2,
the install on the owner's two machines with one model served, has not run. Nothing was
installed, built or run for this record, and it builds nothing in the product.

## Summary

- Mesh-LLM is a Rust program that pools GPUs over iroh QUIC and gives every node the same
  OpenAI-compatible API on loopback. It routes a request by its `model` field, splits a model
  that fits no single machine into layer ranges, and runs on macOS (Apple Silicon), Windows and
  Linux. Licence Apache-2.0. Latest release v0.80.0 of 2026-11-16.
- By its documents it already does what LLM-1, LLM-3 (for models), LLM-4, LLM-5, LLM-6 and
  LLM-9 plan, and part of LLM-7, LLM-10, LLM-13 and LLM-14. It does not do LLM-8, LLM-11 or
  LLM-12.
- Its access control is opt-in. By default a join token locates a mesh but does not authorize
  a node, and the trust policy is off. A cluster that uses it must turn on the owner allowlist.
- Recommendation, for the owner under Q54: run Mesh-LLM as a separate process beside
  OxideSwarm, and close the items it covers once part 2 confirms the allowlist and the two
  machines on a real run.

With `serve --auto` it chooses and downloads a model that fits. In a split each node downloads only the layer files of its own stage from a layer package. A worker can also fetch missing package artifacts from the coordinating node, for immutable package references only, checked by size and SHA-256 | `doc`: [README.md, quick start](https://github.com/Mesh-LLM/mesh-llm/blob/dc8a8fafb8bd51efc287840a84b764c35346b21b/README.md#L75-L83); [USAGE.md, specifying models](https://github.com/Mesh-LLM/mesh-llm/blob/dc8a8fafb8bd51efc287840a84b764c35346b21b/mesh/docs/USAGE.md#L135-L146); [SKIPPY_SPLITS.md, peer artifact transfer](https://github.com/Mesh-LLM/mesh-llm/blob/dc8a8fafb8bd51efc287840a84b764c35346b21b/skippy/docs/SKIPPY_SPLITS.md#L367-L380) |
| Does a node need the file? | Yes. A whole model is loaded from a file on that node. A stage of a split is materialized as a GGUF in a disk cache before it loads. A header pins one provider. One HTTP request per client connection | `doc`: [DESIGN.md, multi-model and HTTP contract](https://github.com/Mesh-LLM/mesh-llm/blob/dc8a8fafb8bd51efc287840a84b764c35346b21b/mesh/docs/design/DESIGN.md#L127-L153); [PROVIDER_SELECTION.md](https://github.com/Mesh-LLM/mesh-llm/blob/dc8a8fafb8bd51efc287840a84b764c35346b21b/mesh/docs/PROVIDER_SELECTION.md); `pr`: [2856](https://github.com/Mesh-LLM/mesh-llm/pull/2856), merged 2026-11-12, in v0.80.0 |

Activations cross between stages directly, not through the host. Only architectures on a certified list are split, unless an override flag is given. It uses its own stage transport (Skippy, on a patched llama.cpp), not llama.cpp's RPC backend | `doc`: [SKIPPY_SPLITS.md, mental model and certified architectures](https://github.com/Mesh-LLM/mesh-llm/blob/dc8a8fafb8bd51efc287840a84b764c35346b21b/skippy/docs/SKIPPY_SPLITS.md#L7-L45); [DESIGN.md, B2B direct transfer](https://github.com/Mesh-LLM/mesh-llm/blob/dc8a8fafb8bd51efc287840a84b764c35346b21b/mesh/docs/design/DESIGN.md#L295-L305); [skippy/README.md](https://github.com/Mesh-LLM/mesh-llm/blob/dc8a8fafb8bd51efc287840a84b764c35346b21b/skippy/README.md#L33-L40) |
| What authenticates a node? | Each node has an iroh endpoint key, and QUIC encrypts all traffic between nodes end to end; a relay cannot read it. A new peer is quarantined until it sends valid gossip. Admission beyond that is opt-in: owner keys (`mesh-llm auth init`), a trust policy (`off` by default, `require-owned`, or `allowlist` of owner ids), and optional creation-time requirements (signed release builds, signed gossip). ## Licence, and how OxideSwarm could use it

- **Licence:** Apache-2.0 (`api`;
  [LICENSE](https://github.com/Mesh-LLM/mesh-llm/blob/dc8a8fafb8bd51efc287840a84b764c35346b21b/LICENSE)).
  OxideSwarm is MIT OR Apache-2.0. Apache-2.0 allows both uses below. This is not legal advice.
- **As a library:** `mesh-llm-sdk` is on crates.io at 0.78.1 of 2026-10-05, behind the v0.80.0
  release (`api`). Its serving role loads the native llama.cpp runtime into the calling process
  ([SDK README](https://github.com/Mesh-LLM/mesh-llm/blob/dc8a8fafb8bd51efc287840a84b764c35346b21b/mesh/crates/mesh-llm-sdk/README.md)).
  Design 0062 (D3) keeps llama.cpp out of the worker's process, so that an abort in llama.cpp
  ends a model process and not the worker. Both projects lock iroh 1.4.1 at the read commits
  (each `Cargo.lock`); that does not show that they combine in one binary.
- **As a separate process:** Mesh-LLM installs and runs as its own background service on
  macOS, Linux and Windows (`mesh-llm setup --service`,
  [USAGE.md, setup](https://github.com/Mesh-LLM/mesh-llm/blob/dc8a8fafb8bd51efc287840a84b764c35346b21b/mesh/docs/USAGE.md#L110-L114)).
  A program reaches it at `http://127.0.0.1:9337/v1`. This is the use this record recommends.
  OxideSwarm then neither starts nor supervises it, and nothing of it enters the Cargo build.

Two consequences for OxideSwarm:

- Mesh-LLM's owner keys are a second identity system beside the cluster secret and the machine
  keys of ENROLL-1. Model traffic would not pass the grid's handshake. G3 of design 0038 asks
  that it does. With Mesh-LLM, the allowlist takes that role, and the owner decides whether
  that is enough (Q54).
- A task under `--isolation off` or `fs` on a worker that also runs Mesh-LLM can reach
  `127.0.0.1:9337` without any check, as design 0061 notes for any loopback model server.
  `fs+net` closes that.
